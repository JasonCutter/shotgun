회의 상태: 완료
결정일: 2026-07-14
### 확정 결정
1. 파일명·확장자, 업로드 MIME과 URL 응답 Content-Type은 선언 신호로 취급하며 실제 형식의 단독 증거로 신뢰하지 않는다. 가능한 경우 파일 바이트 시그니처와 컨테이너 구조를 가장 우선하고, MIME, 확장자와 제한된 텍스트 구조 신호를 함께 비교한다.
2. 형식 판정은 실제 콘텐츠 추출·렌더링·실행과 분리한다. 식별에 필요한 최소 바이트와 컨테이너 표식만 읽으며, 형식이 확인됐다는 사실은 인코딩·구조 무결성·안전성·추출 가능성까지 통과했다는 의미가 아니다.
3. 판정 기록은 declared_format, detected_format, format_family, detection_method, format_confidence, format_mismatch를 분리한다. 선언값과 감지값은 모두 Provenance와 검증 기록으로 보존하고 한 값으로 덮어쓰지 않는다.
4. format_confidence는 확률 점수가 아니라 CONFIRMED, PROBABLE, AMBIGUOUS와 같이 근거의 명확성을 나타내는 열거 상태로 사용한다. Section 2.1 판정 상태는 CONFIRMED, CONSISTENT, AMBIGUOUS_TEXT, MISMATCH, UNKNOWN, UNSUPPORTED로 구분한다.
5. 사용자가 이름을 가진 업로드 파일로 제출한 경우 확장자와 실제 감지 형식이 다르면 실제 형식도 지원 대상이더라도 모두 MISMATCH로 차단하고 사용자에게 알린다. 시스템은 확장자를 자동 변경하거나 실제 형식으로 조용히 라우팅하지 않는다. 원본 이름과 바이트는 변경하지 않는다.
6. 형식 별칭은 불일치로 판단하지 않는다. .jpg와 .jpeg, .html과 .htm, .yaml과 .yml, .mht와 .mhtml은 각각 동일한 형식의 확장자 별칭이다.
7. 직접 파일 URL은 URL에 확장자가 없더라도 바이트 근거로 정식 지원 형식이 확인되면 허용한다. URL에 명시적 지원 확장자가 있는데 실제 바이트 형식이 다르면 차단한다. 서버 Content-Type과 바이트가 충돌하면 바이트를 우선하되 MIME 불일치를 기록한다.
8. 일반 .zip, .rar, .7z 등 압축 파일은 입력받지 않는다. 다만 DOCX·XLSX·PPTX는 정식 지원 OOXML 형식이므로 ZIP 시그니처만으로 판정하지 않고 \[Content_Types\].xml, 관계 파일과 word/, xl/, ppt/ 등 필요한 최소 컨테이너 표식을 확인한다. 임의 파일을 실행하거나 자료 묶음으로 풀어 별도 Source Item을 생성하지 않는다.
9. 일반 ZIP, 다른 ZIP 기반 형식, 필요한 OOXML 표식이 없는 컨테이너는 UNKNOWN 또는 UNSUPPORTED로 분류한다. 손상 여부와 압축 폭탄·경로 순회·과도한 엔트리 등 안전성은 Section 2.3과 2.4에서 판정한다.
10. .json, .xml, .html, .htm은 제한된 시작 구조와 선언 정보를 형식 신호로 사용할 수 있으나 전체 문법 유효성은 Section 2.3에서 검사한다. .txt, .md, .csv, .yaml, .yml은 내용만으로 완전히 구별되지 않을 수 있으므로 선언 확장자를 유지하고 CONSISTENT 또는 AMBIGUOUS_TEXT를 허용한다.
11. 의미 분석이나 AI 분류를 실제 형식 판정에 사용하지 않는다. 텍스트인지 여부와 문자 인코딩 가능성은 Section 2.2에서 검증하고, 구조가 선언 형식과 명백히 다를 때만 MISMATCH로 처리한다.
12. PNG, JPEG, WebP는 매직 바이트와 최소 헤더로 식별한다. 이미지 디코딩 가능 여부와 손상은 Section 2.3, 메타데이터·임베디드 프로파일의 안전성은 Section 2.4에서 다룬다.
13. .mht와 .mhtml을 MHTML_WEB_ARCHIVE 정식 지원 형식으로 추가한다. 유효한 MIME 구조와 웹 문서 루트 HTML 파트를 확인해야 하며, 단순히 확장자가 .mht 또는 .mhtml이라는 이유만으로 통과시키지 않는다.
14. MHTML 내부의 HTML·이미지·스타일 등 포함 자원은 이후 파싱 대상일 뿐 실행하지 않는다. JavaScript, ActiveX, 플러그인 콘텐츠를 실행하지 않고, 파일 내부에 남은 외부 URL을 자동 방문하거나 추가 다운로드하지 않는다. 포함되지 않은 외부 자원은 미확보 상태로 남긴다.
15. MHTML이 일반 이메일형 MIME 자료이거나 유효한 웹 문서 루트 HTML을 확인할 수 없으면 UNKNOWN 또는 MISMATCH로 차단한다. MIME 파트의 문자 인코딩·전송 인코딩은 Section 2.2, 구조 무결성과 외부 참조 안전성은 Section 2.3\~2.4에서 검증한다.
16. Section 2.1 출력에는 원본 파일명 또는 제출 URL, 선언 확장자·MIME, 최종 URL 응답 MIME, 감지 형식과 상위 형식군, 판정 상태와 감지 방법, 불일치·모호성 플래그, 검사기 버전, 다음 검증 진행 가능 여부와 사용자 사유 코드 후보를 포함한다. 원본 바이트와 이름은 변경하지 않는다.
### 결정 근거
확장자와 MIME은 쉽게 잘못 지정되거나 위장될 수 있으므로 바이트와 컨테이너 근거를 우선해야 한다. 동시에 선언값을 제거하지 않고 감지값과 함께 보존하면 사용자의 원본 제출과 시스템 판단 차이를 추적할 수 있다. 초기 버전에서 업로드 파일 불일치를 자동 교정하지 않고 차단하면 잘못된 라우팅과 위장 파일을 단순하고 예측 가능하게 통제할 수 있다. MHTML은 웹페이지를 하나의 파일로 보관하는 실제 사용 가치가 있지만 MIME 기반 컨테이너이므로 루트 웹 문서 확인, 비실행과 외부 자원 미수집 경계가 필요하다.
### 제외한 대안
확장자만 신뢰하는 방식, 선언 형식과 감지 형식을 하나로 덮어쓰는 방식, 지원 형식 불일치를 자동 교정해 계속 처리하는 방식, 모든 직접 파일 URL에 확장자를 요구하는 방식, 일반 압축 파일을 풀어 입력하는 방식, ZIP 시그니처만으로 OOXML을 확정하는 방식, Markdown·CSV·YAML을 AI로 억지 분류하는 방식, MHTML 내부 스크립트 실행과 외부 자원 자동 수집은 채택하지 않는다.
### 영향 범위와 후속 검토
Section 1.2의 정식 지원 형식에 .mht와 .mhtml을 추가했다. Section 2.2는 텍스트·MIME 파트의 문자 인코딩, BOM, 전송 인코딩과 문자 무결성을 검토한다. Section 2.3은 확인된 형식의 손상·암호화·빈 자료·구조 처리 가능성과 MHTML MIME 경계 구조를 검토한다. Section 2.4는 OOXML·MHTML 컨테이너, 스크립트·외부 참조·압축 위험과 격리 정책을 검토한다. Section 2.7은 판정 상태를 사용자 경고·차단·재시도 흐름으로 연결하고, Step 4는 detected_format과 format_family를 기준으로 변환기를 선택한다.
### 미결사항
Section 2.1의 정책 수준 미결사항은 없다. 형식별 매직 바이트 목록, MIME 매핑 테이블, 검사기 라이브러리와 버전, MHTML 루트 파트 선택 알고리즘과 세부 오류 코드는 후속 기술 설계에서 확정한다.
