### 확정 결정
1. Section 2.3은 Section 2.1에서 정식 지원 형식으로 식별되고, 텍스트 자료는 Section 2.2에서 무손실 디코딩된 Source Item 후보가 해당 형식의 필수 구조를 갖추고 원본 수정 없이 후속 변환기로 전달 가능한지 판정한다.
2. detected_format별 읽기 전용 검증 프로파일을 사용한다. 검증기는 필수 구조를 순회하되 콘텐츠·JavaScript·매크로를 실행하거나 화면 렌더링, 링크 방문, 외부 자원·폰트 다운로드와 네트워크 요청을 하지 않는다. 검증기·파서 이름과 버전을 기록하고 같은 원본과 같은 버전에서 결정적인 결과를 지향한다.
3. 검증은 시간·메모리·중첩 깊이·객체와 엔트리 수 한도 아래에서 수행한다. 한도를 초과해 판정을 끝내지 못한 경우 손상으로 단정하지 않고 VALIDATION_LIMIT_EXCEEDED로 분리한다. 구체적인 자원 한도와 공격성 패턴은 Section 2.4에서 확정한다.
4. 구조적으로 처리 가능하려면 정식 지원 형식, 텍스트의 무손실 디코딩, 필수 헤더·컨테이너·루트·주 문서 구조의 존재, 읽기 전용 검증기의 필수 구조 순회 성공, 암호·키·사용자 상호작용 불필요, 자동 복구나 원본 수정 없이 후속 전달 가능 조건을 모두 만족해야 한다.
5. Section 2.3 상태는 PROCESSABLE, PROCESSABLE_WITH_WARNINGS, EMPTY_CONTENT, CONTENT_SPARSE, ENCRYPTED, PASSWORD_REQUIRED, CORRUPT_OR_TRUNCATED, SYNTAX_INVALID, MISSING_REQUIRED_PART, AMBIGUOUS_STRUCTURE, UNSUPPORTED_FEATURE, REPAIR_REQUIRED, VALIDATION_LIMIT_EXCEEDED로 구분한다. 최종 항목 상태와 사용자 문구 연결은 Section 2.7에서 확정하고, Step 2 통합 출력 계약은 Section 2.8에서 확정한다.
6. 검증기 복구 모드, 손상된 PDF 객체·xref 재구축, ZIP 디렉터리 복원, 잘린 JSON·XML 자동 닫기, CSV 따옴표·행 자동 보정 등 추정 복구가 있어야 열리는 자료는 REPAIR_REQUIRED로 차단한다. 서버는 복구본을 지식 처리 입력으로 사용하지 않으며 사용자가 원래 애플리케이션에서 정상 형식으로 다시 저장해 새 항목으로 제출한다.
7. 주 문서, PDF 페이지 트리, OOXML 워크북·슬라이드 목록, MHTML 루트 HTML 등 필수 구조 하나라도 실패하면 Source Item 후보 전체를 차단한다. 선택적 메타데이터·썸네일·비필수 부속 자원 실패는 주 콘텐츠를 온전히 처리할 수 있고 손실 범위를 명시할 수 있을 때만 PROCESSABLE_WITH_WARNINGS로 통과한다.
8. 경고 통과 시 실패한 선택 자원의 내부 경로·종류·영향 범위를 기록한다. 손상 자원을 삭제하거나 빈 자원으로 대체하지 않는다. 문서의 페이지·시트·슬라이드를 자동으로 여러 Source Item으로 분할하지 않으며 필수 문서 트리에 포함된 페이지·시트·슬라이드 하나가 구조적으로 실패해도 항목 전체를 차단한다.
9. 0바이트 원본과 디코딩 후 공백만 있는 텍스트는 EMPTY_CONTENT로 차단한다. 문법과 필수 구조는 유효하지만 빈 객체·배열·루트, 헤더만 있는 표, 실질 내용이 거의 없는 문서는 CONTENT_SPARSE로 기록하고 후속 단계에 전달할 수 있다. 구조적으로 유효한 단색·투명 이미지는 내용이 없다는 이유만으로 빈 자료로 판정하지 않는다.
10. 일반 텍스트와 Markdown은 Section 2.2의 무손실 디코딩 성공과 비공백 내용 존재를 구조 통과 기준으로 한다. Markdown 문법을 엄격한 스키마처럼 강제하거나 잘못 닫힌 강조·목록 표식 등을 자동 수정하지 않는다. 의미·문서 품질 평가는 이 Section에서 수행하지 않는다.
11. JSON은 전체 입력이 하나의 유효한 JSON 값으로 엄격히 파싱돼야 하며 뒤따르는 비공백 데이터와 구문 오류를 허용하지 않는다. 중복 키처럼 파서마다 결과가 달라질 수 있는 구조는 AMBIGUOUS_STRUCTURE로 차단하고, 빈 객체와 빈 배열은 CONTENT_SPARSE로 기록한다.
12. XML은 하나의 유효한 루트 요소를 가진 well-formed 문서여야 한다. 외부 엔티티·외부 DTD를 가져오거나 네트워크로 해석하지 않으며 관련 안전 정책은 Section 2.4에서 결정한다. 구문 오류와 필수 루트 부재는 차단하고 내용 없는 루트는 CONTENT_SPARSE로 기록한다.
13. YAML은 YAML 1.2 계열의 안전한 구조 파서로 검증하며 임의 객체 생성과 사용자 정의 타입 실행을 허용하지 않는다. 구문 오류와 중복 키 등 결과가 모호한 구조는 차단한다. 앵커·별칭의 과도한 확장 위험은 Section 2.4에서 제한하고 빈 문서는 CONTENT_SPARSE로 기록한다.
14. CSV는 엄격한 인용부호와 행 구조 파서로 전체 자료를 읽을 수 있어야 한다. 닫히지 않은 따옴표, 잘림과 해석 불가능한 행 구조는 SYNTAX_INVALID 또는 CORRUPT_OR_TRUNCATED로 차단한다. 헤더 존재를 필수로 요구하지 않고 단일 열 CSV도 허용하며, 헤더만 있거나 실질 데이터 행이 없는 경우 CONTENT_SPARSE로 기록한다.
15. HTML·HTM은 표준 호환 HTML 파서가 안정적인 문서 트리를 만들 수 있으면 일반적인 오류 복구가 발생해도 PROCESSABLE_WITH_WARNINGS로 통과할 수 있다. W3C 완전 유효성을 필수 조건으로 요구하지 않지만 문서 트리를 만들 수 없거나 주 콘텐츠 구조가 유실되는 경우 차단한다. 스크립트 실행과 외부 자원 수집은 금지한다.
16. MHTML은 유효한 MIME multipart 경계, 웹 문서 루트 HTML 파트와 필요한 MIME 파트 구조를 순회할 수 있어야 한다. 경계 손상, 루트 HTML 부재, 필수 파트 해제 실패는 차단한다. 선택적 포함 자원 누락은 영향 범위를 기록해 경고 통과할 수 있으며 외부 자원은 추가 수집하지 않는다. 이메일형 MIME 자료는 Section 2.1 정책에 따라 지원하지 않는다.
17. PDF는 헤더만이 아니라 객체 구조, xref 또는 동등한 객체 탐색 구조, catalog와 page tree를 읽을 수 있어야 한다. 유효한 페이지 트리가 없거나 필수 페이지 객체가 손상된 경우 차단한다. 복구 모드에서만 열리는 PDF는 REPAIR_REQUIRED, 암호화·암호 요구 PDF는 ENCRYPTED 또는 PASSWORD_REQUIRED로 차단한다.
18. DOCX·XLSX·PPTX는 ZIP 중앙 디렉터리, \[Content_Types\].xml, 관계 파일과 형식별 주 문서 구조를 검증한다. DOCX는 주 문서 파트, XLSX는 workbook과 참조 worksheet, PPTX는 presentation과 참조 slide가 모두 읽혀야 한다. 필수 관계 대상과 페이지·시트·슬라이드 손상은 항목 전체를 차단하고 썸네일·사용자 정의 메타데이터 등 선택 파트 실패만 경고 통과할 수 있다. 암호화 컨테이너와 암호 요구 파일은 차단한다.
19. PNG·JPEG·WebP는 헤더 확인을 넘어 전체 이미지 디코딩이 성공하고 양의 너비·높이와 완전한 필수 이미지 데이터를 가져야 한다. 잘림·손상·필수 청크 실패는 차단하고 선택적 메타데이터·프로파일 읽기 실패는 주 이미지가 완전할 때 경고 통과할 수 있다. 과도한 픽셀 수와 디코딩 자원 위험은 Section 2.4에서 제한한다.
20. 구조 결함·암호화·필수 파트 누락처럼 원본 자체의 결정적 실패는 동일 원본 재시도로 해결하지 않는다. 사용자가 정상 파일로 다시 저장하거나 수정한 원문은 기존 Attempt 재시도가 아니라 Section 1.9 정책에 따른 새 항목 또는 새 IntakeSubmission으로 제출한다. 일시적인 검증 서비스 장애만 동일 원본의 새 Attempt로 재시도할 수 있다.
21. Section 2.3 출력에는 판정 상태, detected_format, 검증기와 버전, 검사한 필수 구조와 결과, 누락·손상된 내부 경로, 경고와 영향 범위, 암호화·암호 요구 여부, 페이지·시트·슬라이드·루트 등 구조 요약, 빈 자료·희박 자료 플래그, 검증 한도 초과 정보, 다음 Section 진행 가능 여부와 사유 코드를 포함한다.
22. 검증 중 생성한 임시 문서 트리, 객체 인덱스, 패키지·파트 목록과 구조 해시는 원본이 아니라 재생성 가능한 검증 산출물로 취급한다. 원본을 변경하거나 정상화된 복구본을 만들지 않으며 영구 저장·버전·재생성 계약은 Step 3에서 확정한다.
23. Source Item 후보는 구조 검증의 원자적 단위다. 필수 구조 일부만 정상이라는 이유로 정상 페이지·시트·슬라이드만 선별해 지식화하지 않는다. 한 항목의 구조 실패는 같은 IntakeSubmission의 다른 정상 항목을 막지 않으며 Section 2.7이 2.1\~2.6 결과를 통합해 최종 검증 상태를 계산한다.
### 결정 근거
Shotgun의 지식 후보는 원문 구조와 근거 위치를 전제로 하므로 검증기가 조용히 복구하거나 문서 일부만 선별하면 제출 원본과 실제 처리 자료가 달라질 수 있다. 필수 구조를 항목 단위로 엄격히 검증하고 선택적 자원 손실만 명시적으로 경고하면 Provenance와 재현성을 지키면서 불필요한 전면 실패를 줄일 수 있다. 형식별 프로파일은 JSON·XML의 엄격한 문법과 HTML의 현실적인 오류 복구처럼 서로 다른 형식 특성을 반영한다.
### 제외한 대안
서버 자동 복구와 복구본 지식화, 손상 구조 자동 보정, 정상 페이지·시트·슬라이드만 부분 추출해 별도 Source Item으로 만드는 방식, 필수 구조 실패를 경고로만 통과시키는 방식, 모든 선택 자원 오류를 항목 전체 실패로 처리하는 방식, HTML에 JSON과 같은 엄격 문법 유효성을 요구하는 방식, 암호 입력·복호화·복구 기능, 바이너리·구조 실패를 텍스트로 강제 변환하는 방식은 채택하지 않는다.
### 영향 범위와 후속 검토
Section 2.4는 검증 샌드박스, 압축 폭탄·과도한 객체·픽셀·중첩, OOXML 매크로·외부 관계, HTML·MHTML 스크립트와 외부 참조, XML 외부 엔티티, YAML 별칭 확장, CSV 수식과 Unicode 표시 공격을 검토한다. Section 2.5는 원본 바이트의 정확 중복을 판정하고 Section 2.6은 중복 발견 시 사용자 선택을 정한다. Section 2.7은 2.1\~2.6 결과를 최종 상태·오류·재시도 계약으로 통합하며 Section 2.8은 Step 2 출력 계약을 확정한다. Step 3은 원본과 검증 산출물의 저장·Attempt·Audit 계약을 정하고 Step 4는 검증 통과 자료에서 실제 콘텐츠와 Source Map을 추출한다.
### 미결사항
Section 2.3의 정책 수준 미결사항은 없다. 형식별 검증 라이브러리와 버전, HTML 경고 기준, CSV 행 일관성 세부 규칙, PDF 객체 탐색 구현, OOXML 필수·선택 파트 표, 이미지 디코딩 라이브러리, CONTENT_SPARSE 세부 기준과 검증 자원 한도는 후속 기술 설계에서 확정한다.
