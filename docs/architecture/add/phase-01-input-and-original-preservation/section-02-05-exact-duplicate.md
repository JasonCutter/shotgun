회의 상태: 완료
결정일: 2026-07-16
승인 방식: Phase 1 잔여 설계회의 준비안의 권장안 일괄 승인
### 확정 결정
1. 정확 중복은 원본 바이트 배열이 완전히 동일한 경우만 의미한다. 파일명·경로·URL·사용자 메모·태그·제출 시각은 정확 중복 판정에 포함하지 않는다. 줄바꿈·Unicode 정규화, 압축 해제, PDF 재저장, 이미지 재인코딩 등 변환 결과의 동일성은 정확 중복으로 사용하지 않는다.
2. 의미상 유사, 부분 중복, 개정판과 동일 Source 여부는 정확 중복과 분리하고 Phase 2의 Stable Source·SourceVersion 판정으로 연기한다.
3. 원본 바이트 해시, 바이트 길이, 해시 알고리즘과 버전을 기록한다. 동일 해시와 길이가 발견되면 저장된 바이트를 비교할 수 있는 경우 최종 바이트 비교까지 성공한 뒤 EXACT_DUPLICATE로 확정한다. 해시 충돌 또는 저장 무결성 불일치는 자동 중복 확정하지 않고 무결성 사건으로 처리한다.
4. 초기 해시 알고리즘은 SHA-256을 구현 후보값으로 두되 영구 정책으로 고정하지 않는다. 알고리즘 교체와 병행 검증을 위해 algorithm_version을 필수로 기록한다.
5. 해시는 임시 원본을 받은 직후 스트리밍 방식으로 계산할 수 있지만, 중복 발견이 Section 2.4 안전성 판정을 우회하지 않는다. 기존 자산이 BLOCKED·QUARANTINED·INDETERMINATE이면 중복 사실만 기록하고 기존 처리 결과를 재사용하지 않는다.
6. 파일은 업로드 원본 바이트, 직접 텍스트는 Section 3.3의 버전화된 원문 표현 바이트, URL은 실제 확보한 스냅샷 바이트를 정확 중복 기준으로 사용한다. 같은 URL 문자열이라는 이유만으로 정확 중복으로 확정하지 않는다.
7. 중복 인덱스는 현재 사용자의 접근 경계를 넘지 않는다. 접근할 수 없는 자산의 존재·제목·경로·프로젝트를 중복 알림으로 노출하지 않는다. 물리 저장 중복 제거와 사용자에게 보이는 논리 중복 판정을 분리한다.
8. 같은 IntakeSubmission 안에 동일 바이트가 여러 번 들어오면 검증·저장은 한 번만 수행할 수 있다. 다만 각 제출 위치, 원래 이름, 선택적 사용자 메모와 접수 시각은 별도 발생·Provenance 기록으로 보존한다.
9. Section 2.5 출력에는 판정, 해시 알고리즘·버전, 해시, 바이트 길이, 비교 방식, 접근 가능한 기존 자산 식별자, 기존 결과 재사용 가능 여부와 사용자 선택 필요 여부를 포함한다.
### 결정 근거
정확 중복을 원본 바이트 완전 일치로 한정하면 원본 동일성과 의미상 동일성을 섞지 않고 재현 가능한 판정을 유지할 수 있다. 물리 저장과 논리적 접수 이력을 분리하면 저장·검증 비용을 줄이면서 사용자 메모와 제출 맥락을 잃지 않는다.
### 제외한 대안
파일명·URL·정규화 텍스트만으로 중복을 확정하는 방식, 해시만 같으면 충돌 가능성을 무시하는 방식, 정확 중복을 새 버전으로 자동 승격하는 방식, 접근 권한 확인 전에 기존 자산 정보를 노출하는 방식은 채택하지 않는다.
### 영향 범위와 후속 검토
Section 2.6은 정확 중복 발견 후 사용자의 재사용·새 맥락·관계 의도·취소 선택을 정한다. OriginalAsset과 IntakeItem의 관계, 내용 주소화 저장과 비파일 원본 직렬화는 Section 3.1\~3.3에서 확정한다.
### 미결사항
정책 수준 미결사항은 없다. 스트리밍 해시 라이브러리, 최종 바이트 비교의 크기별 구현, 해시 인덱스와 권한 필터의 데이터베이스 설계는 구현 계획에서 확정한다.
