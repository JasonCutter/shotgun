회의 상태: 완료
결정일: 2026-07-16
승인 방식: Phase 1 잔여 설계회의 준비안의 권장안 일괄 승인
### 확정 결정
1. 사용자 중심 Step 2 최종 상태는 PASSED, PASSED_WITH_WARNINGS, ACTION_REQUIRED, BLOCKED, INDETERMINATE, CANCELLED로 구분한다. 각 Section의 세부 상태와 복수 reason code는 덮어쓰지 않고 함께 보존한다.
2. BLOCKED 또는 안전성 INDETERMINATE가 하나라도 있으면 일반 후속 처리를 진행하지 않는다. 정확 중복 사용자 선택이 필요하면 ACTION_REQUIRED다. 주 콘텐츠가 완전하고 선택 자원·비실행 요소만 제한되는 경우 PASSED_WITH_WARNINGS가 가능하다.
3. 한 Source Item 후보의 실패가 같은 IntakeSubmission의 다른 정상 항목을 자동 차단하지 않는다. 최종 상태는 항목 단위로 원자적이며 제출 단위는 부분 성공 요약을 가진다.
4. 사용자 오류 설명은 무엇이 확인됐는가, 왜 진행 가능하거나 불가능한가, 어느 부분이 영향을 받는가, 사용자가 할 수 있는 다음 행동은 무엇인가의 순서로 구성한다. 원시 예외·스택·내부 경로·민감값은 일반 메시지에 노출하지 않는다.
5. 서비스 장애, 일시적 URL 획득 실패, 샌드박스 시작 실패와 같은 비결정적 실패는 같은 원본의 새 Attempt로 재시도할 수 있다. 손상·암호화·지원하지 않는 구조·악성 요소와 같은 결정적 결과는 같은 원본에 자동 재시도하지 않는다.
6. 사용자가 수정·재저장·암호 해제한 파일은 기존 Attempt 재시도가 아니라 새 Source Item 후보로 제출한다. 검사기·정책·악성코드 서명 DB 변경에 따른 재검사는 같은 원본의 새 Attempt이며 이전 결과를 덮어쓰지 않는다.
7. 수동 검토는 판정 불가 원인 확인, 잘못된 형식 분류 신고, 메타데이터·중복 관계 선택에 사용할 수 있지만 보안 금지 정책을 임의로 우회하지 않는다. 실행 파일·매크로·명확한 악성코드 탐지는 일반 수동 승인으로 통과시키지 않는다.
8. 수동 결정에는 행위자·시각·근거·영향과 정책 버전을 Audit에 기록한다.
9. 사용자에게 형식 식별, 인코딩, 구조, 안전성, 중복의 단계별 완료·대기·차단 상태를 보여주되 파서 내부 로그와 Agent Activity·Audit 상세 이벤트는 사용자 요약과 분리한다.
10. 최종 결과에는 상태, 세부 reason code, 사용자 메시지 키, 영향 범위, 다음 행동, 재시도 가능성, Attempt·검사기·정책 버전과 중복 선택 결과를 포함한다.
### 결정 근거
세부 검사 상태를 유지하면서도 사용자가 이해할 수 있는 상위 상태를 제공하면 시스템 진단과 사용자 행동을 동시에 지원할 수 있다. 결정적 실패와 일시적 실패를 분리하면 무의미한 반복 처리와 보안 우회를 줄인다.
### 제외한 대안
모든 실패를 하나의 ERROR로 축약하는 방식, 결정적 실패의 무한 자동 재시도, 원시 예외를 사용자에게 그대로 노출하는 방식, 수동 검토로 보안 차단을 해제하는 방식과 제출 전체를 일괄 실패시키는 방식은 채택하지 않는다.
### 영향 범위와 후속 검토
Section 2.8은 이 결과를 버전화된 Step 2 출력 계약으로 묶는다. Step 3은 상태·Attempt·Audit의 영속화와 재처리 계약을 확정한다.
### 미결사항
정책 수준 미결사항은 없다. reason code 목록과 메시지 키, 재시도 backoff·횟수, 수동 검토 UI와 운영 권한은 구현 계획에서 확정한다.
