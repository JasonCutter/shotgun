회의 상태: 완료
결정일: 2026-07-16
승인 방식: Phase 1 잔여 설계회의 준비안의 권장안 일괄 승인
### 확정 결정
1. Step 2는 항목마다 버전화된 ValidatedIntakeCandidate 또는 동등한 통합 출력 객체를 생성한다. 이 객체는 원본을 대체하지 않고 임시 원본 참조와 검증·중복·사용자 선택 결과를 결속하는 파생 기록이다.
2. 최소 필드는 Submission·항목·Attempt 식별자, 변경되지 않은 임시 원본 참조와 원래 이름·URL, 원본 바이트 길이와 해시·알고리즘 버전, 실제 형식과 판정 근거, 인코딩·구조·안전성 결과, 정확 중복 결과와 사용자 선택, 최종 상태·reason code·경고·영향 범위, 선택적 사용자 메모, 시스템 Provenance, 기본 접근·민감도 정책, 적용된 표준 정책·User Directive 참조, 검사기·정책·계약 버전, Step 3 진행 가능 여부와 이유다.
3. Phase 1 입력 단계에는 자료별 처리 지시 필드가 없으므로 출력 계약이 새 입력 지시를 생성하지 않는다. 이후 승인된 User Directive나 표준 처리 정책이 적용되는 경우에만 해당 참조와 버전을 기록한다.
4. 출력은 특정 원본 해시와 Attempt에 결속된다. 검사 결과가 바뀌면 기존 출력을 덮어쓰지 않고 새 Attempt 또는 새 출력 버전을 만든다.
5. PASSED와 허용된 PASSED_WITH_WARNINGS만 일반 승격 경로로 진행한다. ACTION_REQUIRED는 사용자 선택 전 진행하지 않고 BLOCKED와 INDETERMINATE는 일반 원본 승격·Phase 2 처리 경로로 진행하지 않는다.
6. Source Item 후보는 Step 2 출력의 원자 단위다. IntakeSubmission은 여러 항목 결과를 묶는 요약을 가질 수 있으며 정상 항목은 실패 항목과 독립적으로 Step 3로 진행할 수 있다.
7. 동일 원본·동일 정책과 검사기 버전·동일 Attempt 입력에 대해 출력은 결정적으로 재생성 가능해야 한다. 명시적 schema_version을 두고 지원하지 않는 버전은 조용히 해석하지 않고 거부하거나 명시적으로 마이그레이션한다.
8. Step 2 완료 조건은 2.1\~2.5 검사 결과 존재, 필요한 2.6 사용자 선택 완료, 2.7 최종 상태·다음 행동 확정, 출력 스키마 검증 통과, 경고·제한·근거·버전 결속과 Audit 이벤트 기록이다.
### 결정 근거
Step 3가 각 검사기의 내부 표현에 직접 의존하지 않고 하나의 명시적 계약만 소비하도록 하면 검사기 교체와 버전 변경에도 단계 경계를 유지할 수 있다.
### 제외한 대안
Step 3가 2.1\~2.7의 개별 테이블과 로그를 직접 조합하는 방식, 스키마 버전 없이 암묵적으로 필드를 해석하는 방식, 제출 전체를 단일 원자 단위로 처리하는 방식은 채택하지 않는다.
### 영향 범위와 후속 검토
Section 3.1은 ValidatedIntakeCandidate에서 OriginalAsset과 IntakeItem을 생성하는 경계를 정한다. 구현 시 JSON Schema 또는 동등한 타입 검증 도구를 사용하되 구체 도구는 구현 계획에서 선택한다.
### 미결사항
정책 수준 미결사항은 없다. 정확한 필드명·타입·열거값·하위 호환 규칙은 구현 계획과 API 스키마에서 확정한다.
