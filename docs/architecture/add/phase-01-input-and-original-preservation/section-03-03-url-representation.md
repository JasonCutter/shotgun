회의 상태: 완료
결정일: 2026-07-16
승인 방식: Phase 1 잔여 설계회의 준비안의 권장안 일괄 승인
### 확정 결정
1. 파일 바이트가 없는 입력은 버전화된 OriginalRepresentation 또는 동등한 봉투 구조를 사용한다. 표현 유형·스키마 버전, 사용자가 제출한 원문 값, 서버 접수 시각, 결정적 직렬화 바이트·해시와 채널별 추가 자산 참조를 기록한다.
2. 직접 텍스트는 제출 시점 편집기 문자열을 원본으로 고정하고 서버가 정한 버전화된 UTF-8 직렬화로 저장·해시한다. 후속 공백·줄바꿈·Unicode 정규화는 파생 결과이며 원본을 바꾸지 않는다.
3. URL 입력은 사용자가 제출한 URL 요청 기록과 실제로 확보한 응답·문서 스냅샷 자산을 분리한다. 같은 URL에서 여러 시각의 서로 다른 스냅샷이 생성될 수 있으며 URL 문자열만으로 같은 OriginalAsset으로 합치지 않는다.
4. URL 요청 기록에는 제출 URL 원문, 최종 URL, 리디렉션 체인, 획득 시각, HTTP 상태, 콘텐츠 유형, 응답 해시, 접근 결과와 정책 버전을 기록한다. 인증 토큰·Cookie·Authorization·민감 헤더는 저장하지 않는다.
5. 본문·자막·스크립트를 확보하지 못한 URL은 URL 요청 기록만 보존할 수 있다. 제목·설명만 확보한 경우 확보 범위를 명시하고 전체 본문 원본처럼 취급하지 않으며 후속 처리에는 실제 확보한 범위만 전달한다.
6. 대화 자료는 독립 채널이 아니라 파일·텍스트·URL로 접수된 MaterialKind이므로 실제 접수 채널의 원본 표현 규칙을 사용한다. 대화 자료라는 성격과 출처·화자 정보는 Provenance 후보로 기록하고 ADR-001의 의견·참고 전용 정책을 유지한다.
7. 비파일 직렬화는 결정적이고 schema_version을 가진다. 필드 순서·문자 인코딩·줄바꿈 규칙을 구현 계약으로 문서화하며 직렬화 버전이 바뀌면 기존 해시와 조용히 섞지 않는다.
### 결정 근거
URL의 현재 위치와 당시 확보 콘텐츠를 분리하고 직접 텍스트를 결정적 바이트 표현으로 고정해야 파일 입력과 같은 무결성·중복·Provenance 계약을 적용할 수 있다.
### 제외한 대안
URL 문자열만 원본으로 저장하는 방식, 현재 URL을 다시 방문해 과거 원본을 복원하는 방식, 직접 텍스트를 정규화한 뒤 원본으로 저장하는 방식은 채택하지 않는다.
### 영향 범위와 후속 검토
URL 스냅샷의 실제 콘텐츠 추출은 Phase 2 Step 4에서 수행한다. 직렬화 형식의 구체 필드와 Canonical JSON 사용 여부는 구현 계획에서 정한다.
### 미결사항
직렬화 표준, URL 응답 헤더 최소 보존 목록, 대용량 스냅샷의 본문·메타데이터 분리 방식은 구현 검증 대기다.
