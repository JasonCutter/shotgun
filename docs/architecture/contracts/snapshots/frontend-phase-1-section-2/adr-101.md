## Confirmed contract

- Every frontend write uses a versioned `FrontendCommandRequest`.
- The browser does not construct the internal Kernel `CommandEnvelope`.
- Request meaning includes envelope and command schema versions, `clientRequestId`, `idempotencyKey`, Project context, policy binding, typed preconditions, correlation context, issue time, and typed payload.
- `commandId` is server-created and is not an initial browser request field.
- `clientRequestId` identifies request/outcome resolution; `idempotencyKey` identifies one logical mutation intent.
- The server computes `commandSemanticDigest`. Reusing a key with different semantics is rejected.
- New Resources bind to the active Project at submission. Existing Resource mutations bind to the Resource Project.
- Principal, actor, capability, and security context come from the server session. CSRF is transport security, not durable command payload.
- A scalar expected revision is replaced by one or more typed preconditions validated atomically.
- The server records accepted Principal, Project, and Policy contexts as well as correlation, causation, and optional trace context.
- Outcomes are `ACCEPTED`, `COMPLETED`, `REJECTED`, or `OUTCOME_UNKNOWN`; completion disposition remains distinct from domain success.
- Recovery order is existing command/dedup ledger, then expected domain resource. Automatic resubmission with a new key is prohibited.
- Transport retry reuses the same request. Domain retry is a new command and attempt.
