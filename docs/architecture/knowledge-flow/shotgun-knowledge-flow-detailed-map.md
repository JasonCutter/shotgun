# Shotgun Knowledge Flow Detailed Map

## Shotgun 지식 처리 상세 흐름 명세 · 작업용 초안 v0.3

## 문서 관리

상태: 작업용 초안 v0.3 — ADD 작성·Frontend 구현 순서 안내용
기준 문서: Shotgun Knowledge Flow 기준본 v1.0
작성일: 2026-07-12
구조: 6개 Phase · 22개 Step · 178개 검토 항목 후보(필수 회의 수 아님)
주의: Section은 ADD 작성 중 확인할 검토 항목이다. 관련 항목은 한 회의에서 병합할 수 있고, 설계 결과에 따라 이름·순서·수가 바뀔 수 있다.
기존 ADD의 세부 항목은 실제 설계 과정에서 이 맵과 비교해 필요한 경우에만 재정렬한다.

## 1. 문서 목적

Baseline Flow와 ADD 사이의 중간 기준 문서로서, 각 Step을 어떤 독립 검토 단위로 나눌지 정의한다.
이 문서는 구현 기술이나 최종 Section 구조를 확정하지 않는다. ADD 작성 시 무엇을 검토할지 놓치지 않도록 진행 순서와 질문 목록을 제공한다.

## 2. 계층 정의

Phase: 지식 처리 생명주기의 큰 구간이며, 처리 상태가 의미 있게 달라지는 경계다.
Step: Phase 안에서 수행되는 주요 처리 책임 또는 상태 전환이다.
Section: Step의 아키텍처를 설계하기 위해 독립적으로 검토하고 승인할 수 있는 결정 단위다.
ADR: Section 검토 중 확정된 중요 아키텍처 결정의 맥락, 대안, 영향과 변경 이력을 기록한다.

## 3. Section 설계 원칙

* 전략회의는 한 번에 하나의 Step 또는 밀접한 Section 묶음만 검토한다.
* Section은 독립 검토가 가능한 크기를 지향하되, 실제 설계에서 밀접한 항목은 병합할 수 있다.
* Section은 구현 태스크가 아니라 데이터·정책·사용자 흐름·시스템 책임의 설계 결정 단위다.
* 각 Section은 상세 설계 전에 반드시 완성할 문서 단위가 아니라, ADD 작성 시 확인할 질문 묶음으로 사용한다.
* Step의 Section 수를 인위적으로 동일하게 맞추지 않는다.
* 확정되지 않은 후보를 ADD의 확정 설계처럼 기록하지 않는다.

## 4. 전체 Section 인덱스

아래 목록은 ADD 작성 시 빠뜨릴 주제를 줄이기 위한 작업용 체크리스트다. Step 1부터 순서대로 보되, 설계 중 병합·이동·삭제할 수 있다.

### Phase 1. 입력·원본 보존 — 3개 Step · 25개 Section 후보

#### Step 1. 파일·텍스트·URL·대화 입력 — 9개 Section 후보

* 1.1 지원 입력 채널과 자료 범위 — 초기 버전에서 접수할 입력 채널·자료 유형과 연기·제외 범위를 정한다.
* 1.2 파일 입력 — 단일 파일 업로드, 확장자 표시, 크기 제한과 파일 선택 경험의 책임 범위를 정한다.
* 1.3 직접 텍스트 입력 — 붙여넣기·직접 작성 텍스트의 제목, 본문, 임시 저장과 제출 방식을 정한다.
* 1.4 URL 입력 — 웹페이지·온라인 문서·GitHub·온라인 PDF 등 URL 접수 범위와 현재 URL 단위 입력 원칙을 정한다.
* 1.5 대화 입력 — AI 대화, 메신저, 이메일, 회의 대화의 붙여넣기·내보내기 파일·공유 URL 접수 방식을 정한다.
* 1.6 복수 자료·폴더·감시 입력 — 여러 파일 동시 입력의 초기 범위와 폴더 가져오기·자동 감시의 연기 여부를 정한다.
* 1.7 사용자 지정 메타데이터 — 프로젝트, 자료 성격, 작성자·화자, 날짜, 태그, 접근 범위와 민감도 입력 정책을 정한다.
* 1.8 자료별 처리 지시 — 이번 입력에만 적용되는 처리 지시와 장기 User Directive 후보의 경계를 정한다.
* 1.9 입력 화면·완료 조건·책임 경계 — 입력 UI, Intake Queue 진입 조건과 Step 1에서 하지 않는 일을 확정한다.

#### Step 2. 형식·인코딩·안전성·정확 중복 확인 — 8개 Section 후보

* 2.1 실제 형식 식별 — 확장자·MIME·파일 시그니처를 이용해 실제 형식과 위장 형식을 구분한다.
* 2.2 인코딩·텍스트 무결성 — 문자 인코딩, 깨진 문자, 줄바꿈, 바이너리 오인식과 복구 가능 범위를 정한다.
* 2.3 구조적 처리 가능성 — 손상 파일, 암호화 문서, 빈 자료, 과대 파일과 지원하지 않는 구조의 판정 규칙을 정한다.
* 2.4 안전성 검사 — 악성 파일, 위험한 압축, 실행 콘텐츠, 외부 참조와 격리·차단 정책을 정한다.
* 2.5 정확 중복 식별 — 원본 바이트 해시를 기준으로 완전히 동일한 입력을 판정하는 규칙을 정한다.
* 2.6 중복 발견 시 사용자 선택 — 기존 자료 재사용, 새 버전 후보, 별도 자료 등록, 취소의 사용자 흐름을 정한다.
* 2.7 검증 결과·오류·재시도 — 통과·경고·차단 상태, 사용자 설명, 재시도와 수동 검토 조건을 정한다.
* 2.8 Step 2 출력 계약 — 검증 결과와 다음 Step으로 전달할 최소 데이터 및 불변 조건을 정한다.

#### Step 3. 원본 자산·IntakeItem 생성, 원본 보존 — 8개 Section 후보

* 3.1 OriginalAsset·IntakeItem 경계 — 원본 자산과 처리 대기 레코드의 역할, 필드와 생명주기를 구분한다.
* 3.2 불변 원본 저장 — 원본 바이트를 변경 없이 저장하고 내용 주소화·체크섬으로 무결성을 보장하는 원칙을 정한다.
* 3.3 URL·비파일 원본 표현 — URL 스냅샷, 직접 텍스트, 대화 입력을 원본 자산으로 표현하는 방식을 정한다.
* 3.4 접수 Provenance·메타데이터 — 입력자, 시각, 입력 채널, 원래 이름·URL, 처리 지시와 정책 버전을 기록하는 범위를 정한다.
* 3.5 접근 범위·민감도 보존 — Step 1에서 지정한 접근 범위와 민감도의 저장·상속·변경 규칙을 정한다.
* 3.6 상태·멱등성·재처리 — IntakeItem 상태 머신, 중복 실행 방지, 취소·재시작·재처리 정책을 정한다.
* 3.7 보존·삭제·격리·복구 — 원본 보존 기간, 논리 삭제, 격리 자산, 백업과 복구 원칙을 정한다.
* 3.8 Phase 2 인계 계약 — Stable Source 미확정 상태에서 변환 단계로 전달할 식별자와 완료 조건을 정한다.

### Phase 2. 변환·근거화 — 4개 Step · 31개 Section 후보

#### Step 4. 콘텐츠 추출·정규화·Source Map 동시 생성 — 8개 Section 후보

* 4.1 변환기 선택과 라우팅 — 입력 형식·버전에 따라 변환기를 선택하고 폴백하는 책임을 정한다.
* 4.2 형식별 원문 콘텐츠 추출 — 텍스트, 문단, 표, 셀, 슬라이드, 이미지 등 형식별 추출 범위를 정한다.
* 4.3 정규화 규칙 — 줄바꿈, 공백, 문자, 목록, 표와 코드의 표준 표현 및 원문 보존 경계를 정한다.
* 4.4 구조 보존 변환 — 제목 계층, 표·셀, 페이지·슬라이드, 화자 구간 등 의미 구조를 유지하는 원칙을 정한다.
* 4.5 변환 중 Source Map 생성 — 모든 정규화 결과를 원본 위치로 되돌릴 수 있도록 동시 매핑하는 규칙을 정한다.
* 4.6 파생 산출물·캐시·재현성 — 추출물, 중간 파일, 변환기 버전과 재생성 가능한 캐시의 보존 정책을 정한다.
* 4.7 부분 실패·폴백·OCR 경계 — 일부 페이지만 실패한 경우, 대체 변환, OCR 사용 조건과 신뢰 표시를 정한다.
* 4.8 변환기 계약과 버전 관리 — 변환기 입력·출력 스키마, 품질 지표, 업그레이드와 재처리 조건을 정한다.

#### Step 5. 문서·언어·화자·표·셀·페이지·시간 구간 분석 — 8개 Section 후보

* 5.1 문서 구조 분석 — 문서·섹션·제목·문단·목록·코드·주석 등 구조 단위를 정의한다.
* 5.2 언어 감지 단위 — 문서·구간·문장 수준 언어 감지와 혼합 언어 처리 원칙을 정한다.
* 5.3 화자·대화 구간 분석 — 화자, 발언 순서, 타임스탬프와 불명확한 화자 표기의 처리 방식을 정한다.
* 5.4 페이지·슬라이드·시각 영역 — 페이지, 슬라이드, 이미지·도형의 좌표와 읽기 순서 분석 범위를 정한다.
* 5.5 표·시트·셀 구조 — 표, 병합 셀, 수식, 시트와 셀 주소를 구조화하는 방식을 정한다.
* 5.6 시간 정보·구간 분석 — 회의·녹취·이벤트의 시각, 기간, 순서와 시간대 처리 원칙을 정한다.
* 5.7 Stable Source·SourceVersion 판정 — 동일 문서의 새 버전인지 새 Source인지 판정하고 SourceVersion을 생성하는 기준을 정한다.
* 5.8 분석 품질·사용자 수정 — 불확실한 구조 분석을 표시하고 사용자가 화자·언어·구조를 교정하는 방식을 정한다.

#### Step 6. Source Map·EvidenceSpan 생성 — 8개 Section 후보

* 6.1 Source Map 표준 스키마 — 원본과 정규화 결과 사이의 위치 매핑 형식과 변환 체인을 정한다.
* 6.2 EvidenceSpan 유형·Locator — 바이트, 줄, 문단, 페이지, 셀, 좌표, 시간 구간별 Locator를 정의한다.
* 6.3 근거 단위와 중첩 — 문장·문단·셀·영역 등 EvidenceSpan의 최소 단위, 중첩과 합성 규칙을 정한다.
* 6.4 무결성·불변성·버전 결속 — EvidenceSpan을 특정 SourceVersion에 고정하고 원본 변경 시 처리 원칙을 정한다.
* 6.5 인용 표시·원문 복귀 — 사용자가 인용에서 원문 위치로 돌아가는 링크·뷰어·하이라이트 경험을 정한다.
* 6.6 검증·고아 근거 처리 — 매핑 불가, 범위 이탈, 손상된 Span을 탐지하고 차단·재생성하는 규칙을 정한다.
* 6.7 형식 간 공통 근거 계약 — 텍스트·표·이미지·오디오 등 서로 다른 형식의 근거를 공통 API로 제공하는 방식을 정한다.
* 6.8 Phase 3 인계 조건 — 후보 생성에 사용할 수 있는 근거의 최소 품질과 완료 상태를 정한다.

#### Step 7. 한국어 번역 생성, 원문과 연결 — 7개 Section 후보

* 7.1 번역 대상·실행 조건 — 어떤 언어와 구간을 언제 한국어로 번역할지 정한다.
* 7.2 원문-번역 정렬 — 번역 문장·구간을 원문 EvidenceSpan과 안정적으로 연결하는 방식을 정한다.
* 7.3 번역 레코드·버전 — 번역문, 원문 언어, 모델·프롬프트·시각·상태와 재번역 이력을 저장하는 규칙을 정한다.
* 7.4 용어·이름·코드·표 처리 — 고유명사, 전문 용어, 코드, 수식, 표와 숫자를 번역할 때의 보존 원칙을 정한다.
* 7.5 품질·실패·부분 번역 — 불확실한 번역, 실패 구간, 폴백 모델과 사용자 표시 방식을 정한다.
* 7.6 사용자 번역 수정 — 사용자 교정의 저장, 이후 재사용과 원문 근거와의 분리 원칙을 정한다.
* 7.7 표시 정책과 Evidence 경계 — 한국어 기본 표시, 원문 접근성과 번역문이 Evidence가 아님을 명시하는 규칙을 정한다.

### Phase 3. 지식 후보 생성 — 2개 Step · 16개 Section 후보

#### Step 8. Claim·Entity·Relation·Event·Decision·Action 후보 추출 — 8개 Section 후보

* 8.1 후보 유형 체계 — Claim, Entity, Relation, Event, Decision, Action과 보조 후보 유형을 정의한다.
* 8.2 추출 단위·범위 — 문장·문단·셀·대화 구간별 후보 생성 단위와 문서 간 추출 범위를 정한다.
* 8.3 후보 스키마·상태 — 후보 ID, 유형, 값, 시간, 범위, 상태, 생성자와 검토 상태를 정의한다.
* 8.4 EvidenceSpan 결속 — 직접 추출 후보가 하나 이상의 정확한 EvidenceSpan을 가져야 하는 규칙을 정한다.
* 8.5 Entity·Alias·Relation 후보 — 개체 동일성, 별칭, 관계 방향·유형과 시간 범위의 후보 표현을 정한다.
* 8.6 Event·Decision·Action 후보 — 사건, 결정, 행동 주체·기한·상태·의존성을 추출하는 범위를 정한다.
* 8.7 모델·비용·배치 전략 — 자료 유형·위험도에 따른 모델 선택, 비용 제한과 병렬·배치 실행 방식을 정한다.
* 8.8 후보 편집·폐기·재추출 — 사용자 수정, 자동 필터링, 재추출과 후보 이력 보존 원칙을 정한다.

#### Step 9. 각 후보의 근거·추론 계보 검증 — 8개 Section 후보

* 9.1 Provenance 유형 — 직접 추출, 사용자 입력, AI 추론, 외부 조사 등 계보 유형을 정의한다.
* 9.2 직접 추출 근거 검증 — 후보 내용이 EvidenceSpan과 실제로 일치하는지 검증하는 규칙을 정한다.
* 9.3 추론 후보 도출 근거 — 사용한 Fact·Claim·EvidenceSpan·Directive·정책과 검증 가능한 도출 요약을 기록한다.
* 9.4 사용자 아이디어·지침 계보 — 사용자 입력 기록을 근거로 삼되 외부 사실 근거와 구분하는 방식을 정한다.
* 9.5 모델·프롬프트·도구·정책 기록 — 재현과 감사에 필요한 실행 메타데이터의 범위를 정한다.
* 9.6 근거 없는 후보·Knowledge Gap — 출처를 추적할 수 없는 후보의 폐기와 근거 부족을 Gap으로 남기는 기준을 정한다.
* 9.7 품질 신호·불확실성 — 추출 정확도, 근거 적합성, 모델 불확실성을 하나의 점수로 합치지 않고 표현하는 방식을 정한다.
* 9.8 검증 게이트·재검증 — Phase 4로 전달할 최소 요건과 모델·정책 변경 시 재검증 조건을 정한다.

### Phase 4. 비교·변경안·승인 — 5개 Step · 39개 Section 후보

#### Step 10. 기존 Canonical 지식·User Directive·Fact Priority와 비교 — 8개 Section 후보

* 10.1 비교 대상 Canonical 범위 — Fact·Claim뿐 아니라 Entity·Relation·Event·Decision 등 비교 대상 자원을 정의한다.
* 10.2 동일 개체·동일 주장 판정 — 후보와 기존 지식의 ID, Alias, 의미·시간 범위를 연결하는 규칙을 정한다.
* 10.3 시간 범위·현재성 비교 — 유효 시작·종료, 사건 시점과 현재 유효 지식을 비교하는 방식을 정한다.
* 10.4 User Directive 적용 — 사용자의 명시적 수정·금지·선호·예외 지침을 비교 과정에 적용하는 우선순위를 정한다.
* 10.5 Fact Priority·출처 우선순위 — 출처 종류, 사용자 지정 우선순위와 상황별 예외를 적용하는 규칙을 정한다.
* 10.6 프로젝트·접근 범위 경계 — 다른 프로젝트·사용자의 지식을 비교 대상에 포함할 수 있는 권한 범위를 정한다.
* 10.7 비교 결과 분류 — 신규, 강화, 수정, 대체, 중복, 충돌, 불확실, 무관 등의 결과 유형을 정한다.
* 10.8 비교 설명·추적 — 어떤 지식·Directive·Priority가 판단에 영향을 주었는지 설명 가능한 기록을 정한다.

#### Step 11. 중복·충돌·시간 유효성·근거 강도 분석 — 7개 Section 후보

* 11.1 중복 유형 — 정확 중복, 표현 중복, 부분 중복, 상·하위 주장과 반복 근거를 구분한다.
* 11.2 충돌 유형 — 직접 모순, 값 차이, 범위·시점 차이, 출처 간 불일치와 정의 충돌을 구분한다.
* 11.3 시간 유효성 — 현재·과거·예정·만료·불명확 상태와 시점에 따라 함께 참일 수 있는 경우를 정한다.
* 11.4 근거 강도 차원 — 직접성, 출처 권위, 독립성, 최신성, 구체성과 재현성을 분리해 평가한다.
* 11.5 출처·Priority 결합 — Fact Priority를 근거 강도와 혼합하지 않고 판단에 적용하는 방식을 정한다.
* 11.6 불확실성·모호성 — 해결 불가능한 모호함을 억지로 단일 결론으로 만들지 않는 표시 규칙을 정한다.
* 11.7 판단 결과 계약 — 후속 Conflict Projection과 ChangeSet이 사용할 구조화된 분석 결과를 정의한다.

#### Step 12. Conflict Projection·Recursive Impact 생성 — 8개 Section 후보

* 12.1 Conflict Projection 모델 — 경쟁 주장, 근거, 우선순위, 시간과 미해결 이유를 사용자에게 보여주는 모델을 정한다.
* 12.2 직접 영향 계산 — 변경 후보가 직접 연결된 Fact·Entity·Relation·Event에 미치는 영향을 계산한다.
* 12.3 재귀 영향 전파 — Graph를 따라 Compiled Truth, 콘텐츠, 일정, 체크리스트와 Action으로 영향을 확장하는 규칙을 정한다.
* 12.4 영향 대상 자원 — 검색 인덱스, 캐시, 답변, 문서, 그래프와 외부 행동 후보 중 갱신 대상을 정의한다.
* 12.5 전파 깊이·성능 한계 — 무한 순환을 막고 깊이, 비용, 시간과 대규모 영향의 처리 방식을 정한다.
* 12.6 오탐·누락 통제 — 약한 관계와 불확실한 연결을 영향 계산에 반영하는 수준과 수동 검토 조건을 정한다.
* 12.7 영향 설명·시각화 — 사용자가 영향 경로와 변경 이유를 이해할 수 있는 트리·그래프·요약 표현을 정한다.
* 12.8 재계산 트리거 — SourceVersion, Directive, Priority, Canonical 변경 시 영향 재계산 조건을 정한다.

#### Step 13. Draft ChangeSet·Burst Diff·영향 미리보기 — 8개 Section 후보

* 13.1 Draft ChangeSet 구조 — 하나의 검토 단위에 포함되는 후보, 작업, 이유, 근거와 상태를 정의한다.
* 13.2 항목 묶음·의존성 — 서로 의존하는 추가·수정·충돌 해결을 묶고 분리 승인 가능성을 표현하는 방식을 정한다.
* 13.3 제안 작업 유형 — 생성, 수정, 종료, 병합, 연결, 충돌 유지·해결과 재생성 작업을 정의한다.
* 13.4 Burst Diff 생성 — 변경 전후 핵심 차이를 압축해 보여주되 근거와 의미 변화를 잃지 않는 규칙을 정한다.
* 13.5 영향·부작용 미리보기 — 직접·재귀 영향, 오래된 결과물, 재생성 대상과 외부 행동 가능성을 표시한다.
* 13.6 비용·모델·Job 미리보기 — 승인 후 필요한 작업, 예상 비용·시간과 모델 선택 정보를 제공하는 범위를 정한다.
* 13.7 검증 상태·잠금·버전 — 검토 중 후보 변경, 동시 수정, 오래된 미리보기와 재검증 조건을 정한다.
* 13.8 검토 화면·접근성 — 항목별 근거, Diff, 영향, 질문과 승인 조작을 제공하는 Review UX를 정한다.

#### Step 14. 승인·수정·보류·거절·지침 추가 — 8개 Section 후보

* 14.1 판단 유형·상태 전이 — 승인, 수정 요청, 보류, 거절, 취소와 재개 상태를 정의한다.
* 14.2 항목별·묶음 승인 — ChangeSet 전체가 아닌 항목별 판단과 의존 항목의 원자적 승인 규칙을 정한다.
* 14.3 사용자 수정 유형 분류 — 표현 수정, 사실 수정, 근거 변경, 범위 변경과 새 Claim을 구분한다.
* 14.4 재검증 라우팅 — 수정 유형에 따라 Provenance, Canonical 비교, 영향 계산으로 되돌리는 경로를 정한다.
* 14.5 User Directive 후보 생성 — 반복될 판단을 장기 지침 후보로 제안하고 별도 승인하는 방식을 정한다.
* 14.6 역할·권한·고위험 승인 — 개인, 프로젝트 구성원, 지정 승인자와 위험도별 승인 권한을 정한다.
* 14.7 판단 이유·댓글·Audit — 사용자 판단의 이유, 코멘트, 시각과 변경 이력을 기록하는 규칙을 정한다.
* 14.8 보류·거절 자료 보존 — 거절된 후보와 근거를 삭제하지 않고 재검토·비교에 활용할 보존 범위를 정한다.

### Phase 5. 공식 지식·확장 — 3개 Step · 24개 Section 후보

#### Step 15. Canonical Fact·Claim 반영·HistoryEvent 기록 — 8개 Section 후보

* 15.1 Canonical 반영 트랜잭션 — 승인 결과, Canonical 변경, HistoryEvent와 후속 이벤트의 원자적 경계를 정한다.
* 15.2 Fact·Claim 반영 규칙 — 승인된 Claim이 자동으로 Fact가 되지 않으며 각 유형을 어떻게 공식 기록하는지 정한다.
* 15.3 Entity·Relation·Event 동시 갱신 — Fact·Claim 변경과 연결된 개체·관계·사건의 일관된 갱신 규칙을 정한다.
* 15.4 충돌·이전 상태 보존 — 이전 Fact, 경쟁 Claim과 해결되지 않은 충돌을 삭제하지 않고 보존하는 방식을 정한다.
* 15.5 HistoryEvent·Revision — 누가 무엇을 왜 바꾸었는지와 변경 전후, 승인 근거를 기록하는 스키마를 정한다.
* 15.6 멱등성·실패·복구 — 중복 승인, 중간 실패, 재시도와 부분 반영 방지 정책을 정한다.
* 15.7 Rollback 제안 — 과거 상태로 직접 덮어쓰지 않고 역변경 ChangeSet을 만드는 원칙을 정한다.
* 15.8 Post-commit 이벤트 — Compiled Truth, 검색, 그래프와 후속 Job 갱신을 시작하는 이벤트 계약을 정한다.

#### Step 16. Compiled Truth·검색·그래프·연결 지식 갱신 — 8개 Section 후보

* 16.1 Compiled Truth 정의·입력 — 활성 Fact·Claim·Directive·Priority·Conflict로 현재 읽기 모델을 만드는 규칙을 정한다.
* 16.2 시간·충돌 표현 — 현재·과거·예정 지식과 미해결 충돌을 Compiled Truth에 표현하는 방식을 정한다.
* 16.3 투영 생성·버전 — Compiled Truth의 생성 버전, 입력 스냅샷, 재현성과 보존 정책을 정한다.
* 16.4 검색 인덱스 갱신 — 정확 검색, 의미 검색, 필터와 인용 연결을 갱신하는 범위를 정한다.
* 16.5 Semantic Graph 갱신 — 노드·관계·상태·시간·근거 수를 그래프 투영에 반영하는 규칙을 정한다.
* 16.6 연결 결과·캐시 무효화 — 답변, 요약, 문서, 추천과 캐시 중 영향받은 파생 결과를 갱신한다.
* 16.7 증분·전체 재생성 — 변경 규모에 따른 최소 갱신과 전체 재구축의 조건을 정한다.
* 16.8 일관성·준비 상태 — Canonical과 모든 투영의 버전 일치, 지연·실패와 사용자 표시 방식을 정한다.

#### Step 17. Knowledge Gap·새 관계·행동 후보 탐색 — 8개 Section 후보

* 17.1 Knowledge Gap 유형 — 누락 사실, 약한 근거, 시간 공백, 정의 불명확과 충돌 미해결을 구분한다.
* 17.2 새 관계·패턴 발견 — 공식 지식에서 아직 명시되지 않은 관계·클러스터·추세 후보를 찾는 범위를 정한다.
* 17.3 확인 질문·행동 후보 — 사용자에게 물을 질문, 조사 과제와 외부 행동 후보를 생성하는 규칙을 정한다.
* 17.4 실행 시점·트리거 — 승인 직후, 주기 작업, 사용자 요청과 특정 변경 시 발견 작업을 실행하는 조건을 정한다.
* 17.5 Provenance·후보 상태 — 발견 결과도 AI 후보이며 근거와 도출 요약을 가져야 하는 규칙을 정한다.
* 17.6 우선순위·비용·억제 — 가치, 위험, 비용, 반복 제안과 사용자의 무시·억제 피드백을 반영하는 방식을 정한다.
* 17.7 Phase 3 재진입 — 발견 결과를 후보 유형 분류와 Provenance 검증부터 다시 통과시키는 계약을 정한다.
* 17.8 Activity·사용자 가시성 — 발견 Job, 진행 상태, 제안 이유와 처리 결과를 보여주는 방식을 정한다.

### Phase 6. 활용·결과·피드백 — 5개 Step · 43개 Section 후보

#### Step 18. 검색·답변·요약·콘텐츠·행동 후보 생성 — 8개 Section 후보

* 18.1 사용 모드 — Canonical, Source 탐색, 외부 조사 모드의 데이터 범위와 표시 차이를 정한다.
* 18.2 질문 해석·검색 계획 — 사용자 의도, 시간·프로젝트 범위와 필요한 검색·그래프·원문 탐색 경로를 정한다.
* 18.3 근거 기반 답변 — 답변을 Canonical 지식과 EvidenceSpan에 결속하고 충돌·한계를 포함하는 규칙을 정한다.
* 18.4 요약·콘텐츠 생성 — 문서·보고서·초안 생성 시 사용 지식, 표현 자유도와 사실 변경 금지 경계를 정한다.
* 18.5 행동 후보 생성 — 일정, 파일, 메시지, 외부 서비스 변경 등 실행 전 Action 후보 스키마를 정한다.
* 18.6 인용·충돌·Gap 표시 — 사용자가 근거, 미해결 충돌, 누락 정보와 사용 모드를 구분해 보는 방식을 정한다.
* 18.7 모델·비용·지연 선택 — 작업 유형, 품질, 위험도, 예산과 응답 시간에 따른 모델 라우팅을 정한다.
* 18.8 대화·결과의 ChangeSet 승격 — 대화 중 새 Claim·수정·결정을 공식 변경안 후보로 전환하는 방식을 정한다.

#### Step 19. 위험도에 따른 자동 제공 또는 사용자 검토 — 8개 Section 후보

* 19.1 위험도 분류 체계 — 정보 제공, 공개, 민감정보, 파일·일정 변경, 금전·법률·의료 등 위험 유형을 정의한다.
* 19.2 분류 입력·정책 — 사용자, 데이터 민감도, 대상, 외부 영향, 되돌릴 수 있음과 Directive를 판단에 사용한다.
* 19.3 자동 제공 가능 범위 — 개인 검색, 읽기, 비공개 초안 등 즉시 제공 가능한 조건을 정한다.
* 19.4 사용자 검토 필수 범위 — 외부 공개, 민감정보, 쓰기 작업, 고위험 조언과 실제 실행의 승인 조건을 정한다.
* 19.5 동의·사전 정책·위임 — 일회 승인, 기간·범위 제한 위임과 언제 재승인이 필요한지 정한다.
* 19.6 설명·경고·대안 — 왜 검토가 필요한지, 예상 영향과 안전한 대안을 사용자에게 설명하는 방식을 정한다.
* 19.7 예외·상향 검토 — 정책 충돌, 분류 불확실성과 사용자의 수동 상향·하향 요청 처리 원칙을 정한다.
* 19.8 판단 Audit·정책 버전 — 위험 판단에 사용한 규칙, 입력, 결정과 정책 변경 이력을 기록한다.

#### Step 20. 화면·문서·내보내기·읽기 API 제공 — 9개 Section 후보

* 20.1 출력 채널·형태 — 화면, 답변, 문서, 파일, 알림, 내보내기와 읽기 API의 책임을 구분한다.
* 20.2 읽기 API 계약 — Canonical·Source·Evidence·Graph·History 조회 자원, 필터, 페이지네이션과 오류를 정한다.
* 20.3 문서·파일 내보내기 — Markdown, HTML, PDF, Office, JSON 등 형식과 투영·원본 포함 범위를 정한다.
* 20.4 인용·계보 패키징 — 내보낸 결과에서도 SourceVersion, EvidenceSpan, 생성 버전과 사용 모드를 보존한다.
* 20.5 접근 제어·마스킹 — 프로젝트·사용자 권한, 민감정보 제거와 부분 공개 정책을 정한다.
* 20.6 버전·재현성 — 출력 스냅샷, 모델·정책·지식 버전과 동일 결과 재생성 가능 범위를 정한다.
* 20.7 대용량·스트리밍·성능 — 긴 결과, 스트리밍, 부분 로딩, 캐시와 취소 UX를 정한다.
* 20.8 접근성·다국어 표시 — 키보드·목록 대안, 한국어 기본 표시와 원문 접근 원칙을 정한다.
* 20.9 공유·게시와 쓰기 경계 — 결과를 외부에 게시하거나 전달하는 행위가 Step 21 승인 대상이 되는 경계를 정한다.

#### Step 21. 승인된 외부 Action 실행·결과 및 Audit 기록 — 9개 Section 후보

* 21.1 Action 유형·Connector 계약 — 메일, 일정, 파일, API, 메시지 등 외부 변경 유형과 Connector 인터페이스를 정한다.
* 21.2 승인·권한 토큰 — 누가 어떤 범위·기간·대상에 실행 권한을 부여했는지 검증하는 방식을 정한다.
* 21.3 실행 전 점검 — 대상, 파라미터, 민감정보, 중복 실행, 정책과 외부 상태를 확인하는 Preflight를 정한다.
* 21.4 실행·멱등성 — 실제 쓰기 호출, idempotency key, 중복 방지와 순서 보장 원칙을 정한다.
* 21.5 재시도·시간 초과·보상 — 부분 실패, 재시도, 취소, 되돌리기와 보상 작업의 가능 범위를 정한다.
* 21.6 결과·외부 ID·증거 — 성공·실패, 외부 객체 ID, 응답, 실행 시각과 확인 가능한 결과를 기록한다.
* 21.7 Audit·History 연결 — Action 후보, 승인, 실행 Job, 결과와 후속 피드백을 하나의 추적 체인으로 연결한다.
* 21.8 비밀정보·Connector 권한 — 자격 증명, 최소 권한, 보관, 회수와 사용자별 Connector 격리를 정한다.
* 21.9 실패 후 사용자 복구 — 재시도, 수정 후 실행, 수동 처리와 지원 정보의 사용자 흐름을 정한다.

#### Step 22. 수정·피드백을 입력·지침·변경안으로 반환 — 9개 Section 후보

* 22.1 피드백 유형 — 사실 수정, 표현 수정, 선호, 평가, 오류 신고, 새 자료와 행동 결과 피드백을 구분한다.
* 22.2 반환 경로 분류 — 피드백을 새 입력, User Directive 후보, Draft ChangeSet 또는 단순 결과 평가로 라우팅한다.
* 22.3 원래 맥락·Provenance 보존 — 어떤 답변·문서·Action·지식에 대한 피드백인지 원문 맥락과 함께 기록한다.
* 22.4 사실·선호·표현 경계 — 사용자 선호를 Fact로, 표현 수정을 지식 변경으로 잘못 승격하지 않는 규칙을 정한다.
* 22.5 승인·검증 재진입 — 피드백 유형에 따라 Step 1, 9, 10, 13 또는 Directive 승인으로 돌아가는 조건을 정한다.
* 22.6 중복·루프 방지 — 동일 피드백의 반복 처리, 자동 제안 순환과 이미 거절한 제안의 재등장을 통제한다.
* 22.7 영향·재처리 — 수정이 기존 Compiled Truth, 답변, 문서와 Action에 미치는 영향을 다시 계산한다.
* 22.8 사용자 상태·결과 표시 — 접수, 검토 중, 반영, 거절과 재처리 결과를 사용자가 추적하는 방식을 정한다.
* 22.9 History·개인화 경계 — 피드백 이력, 취소·철회와 장기 개인화에 사용할 수 있는 범위를 정한다.

## 6. 현재 미결사항

* Stable Source·SourceVersion 판정은 Baseline Flow에 따라 Step 5에서 우선 검토하되, 저장 레코드 생성 책임은 Step 3과 함께 조정한다.
* Step 1 기존 구조는 ADD 작성 시작 시 현재 후보와 비교하여 필요한 부분만 조정한다.
* 공통 관심사는 별도 선행 회의로 고정하지 않고, 관련 Step 설계 중 누적 검토한다.
* 178개 항목은 필수 회의 수가 아니며, ADD 작성 중 필요에 따라 병합·이동·삭제한다.
* Entity Vault는 초기 범위에서 연기된 기능으로 유지하며, 관련 Step에서 필요할 때만 재검토한다.

## 7. 검토·기록 운영 방식

* ADD는 Step 1부터 순서대로 작성하되, 한 번에 하나의 Step 또는 밀접한 Section 묶음만 다룬다.
* 회의에서는 해당 범위의 책임 경계와 필요한 결정을 다루고, Section 이름·수·순서는 결과에 맞게 조정한다.
* ADD에서 확정된 구조 변경이 생기면 Detailed Map에도 반영하고 변경 이력을 남긴다.
* Detailed Map 전체 확정을 기다리지 않고 Step 1부터 ADD 설계를 시작한다.
* 합의된 범위만 ADD에 작성·저장하며, 미결사항과 연기 항목을 분리한다.

## 횡단 아키텍처 확정 기록

Frontend and Human Interaction Architecture가 사용자 승인으로 확정되었다. 이 결정은 새로운 Knowledge Flow Phase를 추가하지 않고, Phase 1~6에 분산된 입력·인용·검토·진행 상태·그래프·출력·접근성 정책을 횡단 Product Frontend Architecture로 연결한다.
확정 경계: 독립 apps/shotgun-web → packages/shotgun-api-client → Shotgun HTTP Command·Query API와 SSE Activity Stream → Shotgun Assembly. Frontend는 Principal·Project·Scope·Sensitivity·Approval·Canonical·Action 권위를 소유하지 않는다.
UI 참조 범위: ddsyasas/llm-wiki는 Source Intake·Ask·Cost·Model·Settings·Home Interaction/Presentation, Inkeep OpenKnowledge는 Visual/Source·2D Graph·Activity·Burst Diff·Preservation Pattern. 두 프로젝트의 전체 Backend·Runtime·Canonical Storage는 제외한다.
현재 assemblies/shotgun-app/src/server.ts의 Inline HTML은 Backend Vertical Slice UI이며 최종 Product UI가 아니다. Frontend 구현은 Knowledge Flow의 6개 지식 생명주기 Phase와 별도의 횡단 구현 축으로 관리한다. 확정 구현 순서는 Shared Contract Foundation(Phase 0) → Frontend Phase 1 Platform Boundary → Phase 2 Knowledge Input·Question → Phase 3 Knowledge Understanding·Editing → Phase 4 Governance·Execution → Phase 5 Operations·Audit → Cross-Phase Product Verification이다. Frontend 5개 Phase는 총 12개 Section으로 진행하며, Phase·Section 번호 순서대로 한 번에 하나의 Section만 구현·검증·승인·병합한다. 기존 Frontend MVP, Review & Activity, Semantic Graph, Visual Editor 명칭은 독립 구현 단계나 완료 판정 단위로 사용하지 않고 필요한 경우 Release Milestone 설명에만 사용한다. 현재 상태는 Shared Contract Foundation 완료이며 다음 구현 Section은 Phase 1 Section 1 — Local Owner Session·Authentication·Project Boundary이다.
Canonical 기록: Notion Project Shotgun ADD 허브의 Frontend and Human Interaction Architecture (확정). 관련 ADR: ADR-095 Accepted.
