## Existing authority and reusable Query surfaces

The implementation is bounded to existing server-authoritative sources and
Product Read composition. The relevant reusable surfaces identified at
kickoff are:

| Existing surface | Intended FE-P3-S1 use |
| --- | --- |
| Stage 6 Canonical Knowledge Query and repository boundaries | Read the canonical knowledge source, snapshots, claims, and history without exposing repository internals to the frontend. |
| Stage 7 `SearchCanonicalKnowledge` and projection/readiness surfaces | Supply server-ranked read/search results and readiness information. |
| Stage 9 `GetKnowledgeGroup`, `ListKnowledgeGroups`, `GetKnowledgeImpact`, and `GetKnowledgeGraph` | Reuse bounded knowledge grouping, impact, and exploration queries where their contracts provide the required evidence. |
| Stage 10 `GetCompiledTruth` and `GetCompiledTruthStatus` | Expose Compiled Truth only as a versioned derived projection with status and lag/reason metadata. |
| `FrontendProductReadCoordinator`, `buildScope`, and existing `ShotgunApiClient` decoding/error patterns | Preserve server-derived Principal, Session, project, access revision, policy revision, and sensitivity scope across Product Read and browser API boundaries. |

The product layer continues to own stable Product View identity, Canonical
identity separation, evidence/lineage meaning, authority labels, validation,
and access masking. Existing module or adapter identifiers must not become
frontend Canonical IDs.

## Kickoff gaps

The initial head contains the implementation request only; no Product code,
database migration, or runtime dependency has been added. The following gaps
are the bounded implementation targets:

1. `FrontendProductReadCoordinator` has no
   `KnowledgeWorkspaceProjectionPort` or Knowledge-specific bounded read
   methods.
2. The contracts package has no strict Knowledge Product View decoder for
   workspace/list, search/filter, stable detail, read-only compare, or
   projection readiness/status responses.
3. `ShotgunApiClient` has no typed Knowledge read client or strict response
   identity validation.
4. The Product API has no versioned Knowledge workspace/list, search/filter,
   detail, or read-only compare endpoints.
5. The existing `/knowledge` route is a guarded placeholder. Replacing that UI
   is outside Slice A and is not evidence for this audit.
6. Existing lineage and projection-status information must be mapped from
   available authoritative Query results. Missing lineage must remain explicit;
   this work must not synthesize lineage or fabricate project identity.
7. Knowledge-specific cache/query identity must include the server-derived
   project, access/policy revisions, sensitivity, and relevant
   canonical/projection revision so project switches cannot reuse another
   scope's result.
