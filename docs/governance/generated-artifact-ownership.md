# Generated Artifact Ownership Policy

## Purpose

Generated output must never become an unexplained second source of truth. Every material generated artifact has an owner, Canonical inputs, a generator, a regeneration or retention rule and a clear authority classification.

## Artifact classes

### `GENERATED_REPRODUCIBLE`

A versioned artifact that can be reproduced deterministically enough from identified Canonical inputs and a pinned generator.

Required metadata:

- target path or path pattern;
- Canonical inputs;
- generator command or implementation;
- generator/version boundary;
- owning subsystem;
- regeneration trigger;
- review and commit rule.

### `GENERATED_TRANSIENT`

An artifact created during CI, local verification or runtime and not committed as authority.

Examples include the CI SBOM temporary file and diagnostic logs. A durable result derived from it must be summarized in a Git evidence record when it supports a material claim.

### `DERIVED_RUNTIME_PROJECTION`

A runtime view regenerated from authoritative records. It is not a writable Canonical source.

Compiled Truth, search indexes, graph views, timelines and Activity projections belong to this class. Their failure or deletion does not delete Canonical Knowledge.

### `APPROVED_SNAPSHOT`

A reviewed contract or decision snapshot frozen for implementation and verification. It may have been created with tooling, but after user approval and Git merge its authority comes from review and approval, not from generator output alone.

Contract snapshots are therefore not automatically disposable generated files.

### `MIGRATED_CANONICAL`

A document exported from a legacy source and promoted through a reviewed Git migration. It records provenance and semantic-change boundaries. After merge, the Git target is Canonical and the external source becomes Reference.

### `LOCKFILE`

A tool-generated dependency resolution committed to make builds reproducible. Its inputs and generator are controlled, but it does not define Product architecture.

## Ownership rules

1. A generated artifact must identify one owning subsystem or governance area.
2. Generated content must not silently overwrite handwritten Canonical decisions.
3. Canonical inputs must be listed and addressable.
4. Generated outputs must be reproducible or explicitly classified as transient/non-reproducible evidence.
5. A generated artifact cannot approve itself.
6. Generator changes that alter semantic output require review, migration impact and rollback consideration.
7. Runtime projections remain replaceable and rebuildable from Canonical records.
8. Sensitive, licensed or large generated artifacts may remain external only with a safe Git manifest entry.
9. Expiring CI artifacts and logs are supporting evidence, not the sole durable record.
10. Deleting a generated artifact must not delete its Canonical inputs or decision history.

## Registered ownership

The machine-readable registry is [`docs/generated-artifacts.json`](../generated-artifacts.json).

Initial registered classes include:

- `package-lock.json` as a versioned lockfile;
- CI `sbom.cdx.json` as transient generated output;
- Compiled Truth as a runtime derived projection;
- approved architecture contract snapshots;
- migrated Knowledge Flow, Frontend Architecture and Phase ADD documents.
- bounded Frontend status projection blocks generated from the Frontend Work Item Registry and Section completion manifests.

## Bounded Markdown projection boundary

The Frontend status generator owns only text between matching `FRONTEND-WORK-ITEM-STATUS` markers in registered Markdown targets. It must not regenerate, normalize, or overwrite the surrounding architecture decisions, implementation plan, historical ADD text, correction notes, or evidence records. The source registry and completion manifests remain the status authority; the Markdown blocks are reproducible views checked for drift in CI.

## Compiled Truth boundary

Compiled Truth is generated from Canonical records and approved projection contracts. It may be rebuilt or replaced without changing Canonical Knowledge. It must not accept direct user or AI writes as if it were the Canonical store.

## Contract snapshot boundary

A draft snapshot generated by tooling is Candidate. A snapshot becomes an approved implementation contract only after the required review, user approval and Git merge. Once approved, it is retained as `APPROVED_SNAPSHOT` and is not automatically regenerated over the same path.

## SBOM boundary

CI creates `sbom.cdx.json` to verify dependency inventory. The file is transient unless a release or audit requires durable retention. Durable claims must record the exact commit, command, result and retained artifact checksum or external location.

## Validation

```text
npm run docs:canonical
npm run docs:validate
```

The documentation validator confirms that registered versioned targets and Canonical inputs exist and that every registry entry has an owner and generator or derivation description.
